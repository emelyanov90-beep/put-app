# БД, backend и сервер «Путь»: состояние и план

Дата обновления: 06.09.2026. Основание: [ТЗ](TZ_Put_Flutter_PocketBase.md),
особенно разделы 12–29, 35, 39–41, и [дополнения](PRODUCT_RULES.md).
В репозитории и на сервере закреплён PocketBase 0.40.2.

## Текущее состояние

- Production-контур работает на `https://pb.bookingtest26.ru`: nginx и HTTPS,
  PocketBase на loopback под отдельным пользователем systemd, UFW и ежедневные
  локальные backup с retention 7.
- Воспроизводимые migrations создают 17 коллекций, access rules, индексы,
  demo seed и runtime-настройки. `pb_data`, бинарник и секреты не входят в Git.
- Серверные actions реализуют OTP `111111`, профиль, автомобили, поездки,
  публикацию/возврат/отмену, поиск, standard/instant бронирование,
  approve/reject, mock pay/refund и чат. Критичные статусы нельзя произвольно
  менять через collection API.
- Flutter выбирает PocketBase repositories при заданном `PB_BASE_URL`; без URL
  остаётся автономный preview для UI-разработки. Production URL передаётся
  через `--dart-define` или файл конфигурации сборки.
- Локальный smoke-тест проверяет чистую миграцию, auth, privacy, цены, поездки,
  гонку за последнее место, идемпотентные pay/cancel и запрет прямого PATCH.
  Read-only production smoke проверяет HTTPS, OTP, runtime config и поиск.

Ниже сохранён исходный подробный checklist. Реализованные пункты служат
регрессионными требованиями. Открытые пункты следующего этапа: полноценный
realtime и offline retry, независимый parcel flow, административные процессы
верификации/возвратов, внешний backup с тестом восстановления, release signing
и E2E на физических Android/iOS устройствах.

## 1. Сначала зафиксировать контракт и границу preview

Результат этапа: API-контракт, схема переходов, список серверных ошибок, отдельные конфигурации preview/staging/release.

- Сохранить архитектуру `UI → Controller/Provider → Repository → PocketBase SDK/custom route`.
- In-memory источники оставлять только preview-адаптерами. При наличии
  `PB_BASE_URL` основные auth/profile/garage/trips/bookings/chat flows используют
  PocketBase repositories.
- В серверном режиме запретить fallback на демонстрационные данные. Отсутствие/невалидность HTTPS URL в release должно останавливать сборку либо показывать конфигурационную ошибку.
- Согласовать DTO поездки, брони и денег до реализации UI оплаты: полная цена, комиссия, сумма водителю, валюта, версия расчёта. Оплачивается mock-комиссия согласно PRODUCT_RULES, не вся поездка. Денежную единицу явно закрепить в контракте; текущий клиент использует целые рубли.
- Добавить в серверную схему связь брони с посадкой/высадкой и снимок расчёта. В минимальной таблице `bookings` из ТЗ этих полей нет, но маршрут пассажира требуется. Индексы из запроса сопоставлять остановкам на сервере, сохранять устойчивые ссылки и защищать от изменения маршрута после брони.
- Поля цены участков/минимальной посадки из PRODUCT_RULES тоже включить в миграцию и расчёт. Убрать расчёт участка как `число участков × 150` из UI.
- Уточнить переход при выключенной монетизации: ТЗ предусматривает `not_required`, текущий новый адаптер принимает только `unpaid/paid`. До реализации этой ветки не включать её в staging.

### Начальный контракт, уже заложенный в клиенте

Контракт ниже подтверждён изолированным PocketBase smoke-тестом и публичным
production smoke-тестом.

| Действие | Запрос | Успешный ответ |
|---|---|---|
| Создать бронь | `POST /api/app/bookings`: `trip_id`, `booking_kind=passenger`, `pickup_index`, `dropoff_index`, `seat_count`, `extra_service_codes` | `booking: {id, trip_id, status, payment_status}` |
| Mock-оплата | `POST /api/app/bookings/:id/pay` | Такая же бронь, `confirmed + paid` |
| Отмена | `POST /api/app/bookings/:id/cancel` | `booking: {id, status: cancelled_by_passenger, payment_status}`, `booking_blocked: bool`, `refund_amount: int` |

Клиент не отправляет готовые `paid/confirmed`, пользователя-владельца или рассчитанную цену. В create/pay поддерживается также плоский ответ; при согласовании API выбрать единую обёртку и убрать неоднозначность. Таймаут клиента — 15 секунд. Поддержанные business codes: `NO_SEATS`, `BOOKING_EXISTS`, `BOOKING_BLOCKED`, `TRIP_UNAVAILABLE`, `OWN_TRIP`; HTTP 401 отображает ошибку сессии. Следующий шаг — единая обработка 401 с refresh/выходом и сохранением намерения пользователя.

Добавить запрос текущей брони/списка заказов, повторное получение состояния после таймаута, ключ идемпотентности и проверку соответствия ответа запрошенной сущности. Текущее подавление двойного тапа не защищает от повторов после перезапуска или сетевого сбоя.

## 2. Воспроизводимая БД и правила доступа

Результат этапа: запуск с пустым `pb_data` автоматически создаёт рабочую схему; seed можно повторить без дублей.

| Группа | Коллекции ТЗ | Обязательная граница доступа |
|---|---|---|
| Учётная запись | `users`, `cities` | Собственный приватный профиль; публичный DTO водителя без телефона и токена |
| Транспорт | `vehicles` | Владелец и администратор; СТС — защищённый файл, не публичная ссылка |
| Каталог | `trips`, `trip_stops`, `extra_services`, `trip_extra_services` | Опубликованные поездки доступны поиску; чужие черновики закрыты |
| Бронь | `bookings`, `booking_extras`, `parcels` | Только участники; переходы статусов только actions |
| Деньги | `payments`, `refunds` | Клиент не создаёт/меняет статус, сумму, владельца или transaction id |
| Общение | `chats`, `messages`, `notifications` | Участники конкретной брони; уведомления только адресату |
| Репутация и настройки | `reviews`, `app_settings` | Публикация отзывов и настройки — администратор; агрегаты серверные |

- Перенести все поля/select из раздела 26 ТЗ, не объединять поездку, бронь, платёж и посылку в одну запись.
- Индексы: unique `users.phone`, `trip_stops(trip_id,sort_order)`, `payments.booking_id`, `chats.booking_id`, `reviews(booking_id,author_id,target_user_id)`; остальные поисковые индексы — раздел 27.
- Защиту дублей активной брони реализовать ограничением/транзакцией с учётом terminal statuses: отменённая бронь не должна навсегда запрещать новую.
- Нельзя полагаться только на `updateRule`: отдельно ограничить чувствительные поля и прямые collection API. Запретить клиенту менять `booking_blocked`, рейтинг, `verification_status`, суммы и критичные статусы.
- Деловые сущности отменять через статус, сохранять историю; не удалять бронь/поездку/платёж физически.
- Seed: минимум две роли, водитель без отзывов, отзывы опубликованные/неопубликованные, approved/pending/rejected авто, standard/instant/full/cancelled поездки, остановки, несколько состояний броней. Телефоны только вымышленные, секреты вне Git.

Проверка: применить миграции и seed дважды на отдельной временной БД; проверить ограничения прямыми запросами гостя, владельца, участника и постороннего пользователя, включая protected file URL и realtime.

## 3. Авторизация, профиль и восстановление

- Реализовать `request-code` и `verify-code`. Код в тестовом scope всегда `111111`, проверяется backend; неверный/неполный код отвергается. Реальный SMS не подключать.
- Нормализовать телефон на сервере, уникальность обеспечить БД, ограничить частоту запросов. Не выдавать superuser token.
- Новый пользователь заполняет профиль; существующий получает свой профиль с сервера. Убрать определение типа входа только по выбранной кнопке клиента.
- Подключить secure auth store, refresh/проверку действительности сессии при старте, logout, истечение токена. Router должен зависеть от реальной auth-сессии, а не `PreviewSessionController`.
- Профиль/аватар/город/роль сохранять через repository, после перезапуска загружать с сервера. Асинхронные ответы старой сессии не должны менять новую.
- Рейтинг вычислять только по опубликованным reviews: при count=0 хранить null и выводить `5 звезд, нет отзывов`.

Проверка: чистая установка → регистрация → редактирование → kill/relaunch → тот же профиль; logout → другой аккаунт без чужих данных; просроченный токен; ошибка secure storage и повтор.

## 4. Гараж, поездки и поиск

- Загрузка фото и СТС: проверка MIME, декодируемости, размера на клиенте и сервере; ошибки/повтор/отмена; доступ к СТС только владельцу и администратору.
- Submit verification — серверный action; только администратор approved/rejected. Изменение авто/СТС требует новой проверки. Публикация повторно проверяет автомобиль на сервере.
- Реализовать create/edit/publish/create-return из раздела 29. Сервер проверяет владельца, точки маршрута, даты, вместимость, настройки цен, approved авто, лимиты публикаций и допустимость редактирования при пассажирах.
- Черновик переживает перезапуск; повтор публикации не создаёт новую поездку и не расходует лимит дважды. Обратная поездка — отдельная запись с `paired_trip_id`.
- Поиск применяет фильтры на backend, возвращает UTC timestamps, остановки, актуальные места, публичные DTO. Убрать статичные майские даты из каталога и строковые даты из domain-моделей.
- Опубликованная водителем поездка появляется у пассажира. Cancel/completed — серверные переходы; статус нельзя определять только часами клиента.

Проверка: неподтверждённое/удалённое авто, уменьшение вместимости, лимит, двойная публикация, обратная поездка, черновик и поиск на втором аккаунте.

## 5. Бронирование и mock-оплата — критический этап

| Режим | Переходы при включённой монетизации | Когда резервируются места |
|---|---|---|
| Standard | create → `pending_driver`; approve → `awaiting_payment`; pay → `confirmed/paid`; reject → `rejected_by_driver` | После approve |
| Instant | create → `awaiting_payment`; pay → `confirmed/paid` | При create |

- Все проверки и изменение мест — в одной серверной транзакции. Проверять собственную поездку, активность, блокировку, корректность маршрута/услуг/числа мест.
- Не принимать цену или статус из UI. Рассчитывать полную цену, extras, комиссию и сумму водителю серверно. Зафиксировать цену брони, не пересчитывать прошлую оплату по новым настройкам.
- Pay доступен только владельцу в разрешённом статусе. Единственный payment на бронь; повтор возвращает прежний результат и тот же mock transaction id.
- После неопределённого исхода запроса клиент сначала получает состояние; повтор безопасен и не создаёт новую бронь/оплату.
- Подключить чтение заказов, ожидание решения, уведомление об одобрении/отказе, доступную оплату, экран успешного результата с реальными суммами. Сейчас новая бронь не попадает в статичный preview-список заказов.

Проверка: две независимые сессии бронируют последнее место одновременно; остаётся ровно одна бронь, резервирующая место. Параллельные approve/pay/retry, чужой pay, direct collection PATCH, crash после отправки запроса, восстановление после перезапуска. Проверки выполнять на реальном PocketBase, не считать mock unit tests доказательством атомарности.

## 6. Отмена, возврат, ограничения и посылки

- Cancel атомарно меняет статус, освобождает резерв, ставит `cancelled_at`; оплаченная бронь создаёт единственную заявку `refund_requested`. Возвращается только mock-комиссия согласно фактически оплаченному payment.
- Повтор cancel не создаёт refund и не увеличивает счётчик повторно. Администратор обрабатывает refund, реальных денег нет.
- Две отмены за скользящие 30 дней блокируют **новые бронирования до решения администратора**. Перезапуск и прямой API не обходят запрет; это не автоматический бан всего аккаунта на 30 дней.
- Раздельно определить правила отмены поездки водителем и отмены брони пассажиром; не переносить локальные счётчики из `DriverTrip` как серверную модель пользователя.
- Посылки реализовать отдельной сущностью, ценой/категорией и `booking_kind=parcel`; не подменять их пассажирскими местами. Закончить соответствующий UI из Figma.

Проверка: неоплаченная/оплаченная бронь, повтор и гонка отмены с оплатой, граница 30 дней, разблокировка администратором, возврат места на втором устройстве, посылка независимо от пассажира.

## 7. Чат, realtime, уведомления

- Чат привязан к `booking_id` и создаётся идемпотентно по правилам раздела 22. Текущий preview-ключ peer+trip заменить; клиент не назначает участников.
- Сервер проверяет отправителя/участие и текст. Стабильный порядок `created_at + id`, локальный client message id для повтора без дубля.
- Подписки на брони, сообщения и уведомления; отмена подписок при logout, повторное подключение и контрольное чтение после background/сети.
- Не показывать успешную отправку до подтверждения сервера; pending/failed/retry в UI. Счётчик прочитанного принадлежит своему пользователю.
- Списки и детали обновлять из одного repository, не передавать устаревший снимок сущности через route extra как единственный источник.

Проверка: два устройства, одобрение/оплата/отмена и сообщения без refresh; потеря сети, очередь повторов, background, перезапуск, запрет чужого чата и чужой realtime-подписки.

## 8. Staging-сервер и сборки

Подготовку инфраструктуры можно вести после согласования схемы параллельно реализации API. Публикация staging — после готовности воспроизводимых миграций и правил доступа.

1. VPS вне РФ, домен staging, DNS; HTTPS reverse proxy (например Caddy), PocketBase на loopback за proxy. Наружу только необходимые порты; процесс под отдельным непривилегированным пользователем, systemd/restart, постоянный data volume.
2. Разделить staging и production, хранить секреты в окружении/секрет-хранилище. Admin UI ограничить; в мобильной сборке нет admin credentials.
3. Версионировать migrations/hooks/seed и deployment instructions. `pb_data`, backend binary, ключи и локальная конфигурация игнорируются Git.
4. Автоматические backup БД и файлов согласованным способом, копия вне VPS, retention; обязательно восстановление на отдельном экземпляре. Перед миграцией backup, откат релиза и восстановление репетировать.
5. Health check, контроль TLS/диска/процесса, логи без телефонов, токенов, СТС и содержимого личных сообщений. Не включать verbose SDK logging в release.
6. Собрать Android с `--dart-define=PB_BASE_URL=https://<staging-domain>` после подключения всех repositories; отдельная release signing config вместо текущего debug-ключа. iOS — unsigned build, затем подпись и физическое устройство.
7. Проверить доступ с телефона через мобильную сеть вне РФ без VPN; с Wi-Fi разработчика этот критерий не подтверждается.

## 9. Приёмка следующего этапа

Готовность определяется AC-01…AC-22 и smoke-test из ТЗ, а не количеством реализованных экранов. До вердикта READY обязательны:

- Полный standard и instant путь на двух аккаунтах с серверными данными.
- Отсутствие перепродажи мест/дубля платежа при конкурентных запросах.
- Запрет чтения/изменения чужих данных и protected файлов прямым API.
- Перезапуск сохраняет профиль, гараж, поездки, бронь, оплату и чат.
- Чат и статусы обновляются без refresh; offline/error/retry воспроизводимы.
- Финальные Figma-экраны без неработающих пунктов, с подключёнными шрифтами/ассетами и проверкой Android 320/375 dp, большого текста и iOS.
- Зелёные Flutter и backend tests, analyze, release build; staging доступен вне РФ; backup восстановлен.

Первый практический заход: **этапы 1–3**. Затем гараж/каталог, потом бронирование/оплата, отмена/посылки и realtime. Не подключать весь существующий UI к пустым коллекциям сразу: завершать каждый вертикальный сценарий вместе с его правилами доступа и тестами.
