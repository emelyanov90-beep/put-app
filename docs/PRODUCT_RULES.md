# Product rules supplied during implementation

These explicit product rules supplement the main TZ and must be considered in
screen flows, transitions, states, and Flutter/PocketBase behavior.

## Onboarding, authorization, and registration

1. Onboarding explains step by step who the application is for and how to use
   it.
2. The registration branch starts from the second onboarding slide, where the
   user is explicitly invited to register.
3. Authorization and registration use a phone number and confirmation code.
4. After phone confirmation, a new user supplies a required name and an
   optional avatar.
5. The new user then chooses the initial action/role: passenger (finding a
   trip) or driver (creating a trip), and selects a city or locality.
6. After the city is selected, the user proceeds to the corresponding section
   of the application.
7. The "Already have an account" action skips onboarding and opens phone
   authorization. After code verification, an existing user proceeds directly
   to the application; if the backend reports an incomplete profile, profile
   creation must be resumed instead.

The backend response after code verification is the source of truth for whether
the account is new, existing, or has an incomplete profile. The UI preview may
simulate both destinations only when the build explicitly enables preview mode.

For the test implementation no real SMS provider is connected. The confirmation
code for every valid phone number is always `111111`.

## Platform priority and delivery

- The current delivery target is Android. The required distributable at the end
  of the test task is an APK.
- Development, visual QA, and release checks should therefore be Android-first.
- Shared Flutter/Dart code must remain cross-platform and avoid unnecessary
  Android-only assumptions.
- A complete iOS version, iOS-specific polish, and iOS release delivery are not
  part of the current scope unless explicitly requested later.

## Создание поездки водителем (легковой автомобиль)

Водитель создаёт поездку пошагово и указывает:

1. Маршрут: пункт отправления, пункт прибытия и 0..N точек запланированных
   остановок в порядке следования.
2. Дату и время отправления. Время выбирается только кратно 30 минутам.
3. Количество пассажиров (мест), доступное к бронированию.
4. Стоимость проезда:
   - от начала и до конца маршрута;
   - отдельную цену для **каждой пары точек маршрута**;
   - минимальную стоимость «за посадку», которая применяется независимо от
     стоимости проезда между остановками.

   Для маршрута A–E с промежуточными B, C, D водитель задаёт цены AB, AC, AD,
   BC, BD, BE, CD, CE, DE и AE — то есть все пары точек. Цена **не** выводится
   из ставки за километр и **не** складывается из более коротких участков:
   чем короче расстояние, тем дороже километр пути, поэтому AC заведомо меньше,
   чем AB + BC. Пара, которую водитель не оценил, не продаётся: пассажир её не
   увидит в листе бронирования.
5. Автомобиль из списка авто, прикреплённых к аккаунту (раздел «Мои
   автомобили»).
6. Дополнительные возможности с оценённой стоимостью: детское кресло, провоз
   животных, провоз багажа, провоз посылки.
   - Для посылки водитель выбирает принимаемые размеры S / M / L; для каждого
     размера указаны максимальные габариты и вес.
   - Водитель может разрешить отправку посылки без проезда пассажира.
7. Способ присоединения пассажира к поездке:
   - стандартное бронирование — водитель получает уведомление о заявке, может
     открыть профиль пассажира, отклонить или подтвердить бронь; после
     подтверждения пассажир получает уведомление о необходимости оплатить
     бронирование банковской картой (онлайн-эквайринг);
   - быстрое бронирование — без подтверждения каждой заявки, пассажир сразу
     оплачивает бронирование банковской картой.

Водитель может сохранить поездку, отредактировать её данные, создать «обратную»
поездку и опубликовать поездку.

Редактирование открывается из «Моих поездок» кнопкой «Изменить» и начинается с
экрана «Изменение заказа» — это тот же шаг маршрута мастера, но с двумя
действиями внизу: «Далее» ведёт по остальным шагам, а «Сохранить» появляется
активной только тогда, когда в поездке что-то действительно изменилось. Цены
правятся на отдельном экране «Изменение стоимости», который открывается кнопкой
«Изменить стоимость». После сохранения показывается зелёное уведомление
«Изменения сохранены», а поездка остаётся в своём состоянии: опубликованная
остаётся опубликованной, черновик — черновиком.

Обратная поездка дублирует всю информацию исходной, маршрут отображается в
обратном порядке, водитель обязан указать новое время старта.

Создаётся она из «Моих поездок» кнопкой «Обратный маршрут» на опубликованной
поездке и открывается отдельным экраном «Обратное направление»: расчёт по
деньгам и маршрут в обратном порядке уже заполнены, дата, время выезда и
примерное время прибытия пустые. Пока они не заданы, «Опубликовать поездку»
недоступна.

Публикация обратной поездки подтверждается листом «Опубликовать поездку?» со
сводкой: точки, количество остановок, дата и время, стоимость поездки,
раскрывающийся список цен между остановками, цена и количество доп. услуг,
автомобиль и тип бронирования. «Отмена» возвращает к редактированию.

После публикации показывается экран «Заказ опубликован!» с остатком лимитов на
сегодня и на неделю и переходом в «Мои заказы».

Публикаций не более N в сутки и не более X в неделю. Значения берутся из
серверной конфигурации `app_settings` (раздел 17 ТЗ) и не хардкодятся в UI.

Дневной лимит считается по направлениям: на легковой автомобиль можно
опубликовать не более одной поездки в сутки в каждом направлении — туда и
обратно (`outbound_limit_per_pair` и `return_limit_per_pair` из раздела 17 ТЗ).
Обратной считается поездка со ссылкой `paired_trip_id`.

Кнопка «Опубликовать поездку» остаётся активной: лимит проверяется по нажатию, и
при исчерпании открывается диалог «Достигнут лимит на сегодня» со счётчиками
«Туда» и «Обратно» и выбором — сохранить поездку как шаблон или отменить.

Мастер по Figma («Новый заказ») состоит из 6 шагов:

1. Тип заказа: «Автомобиль» или «Автобус». Формулировки водительские —
   «взять попутчиков в свою поездку» и «перевозить пассажиров и посылки».
   Пассажирская пара «найти водителя для себя» / «отправить груз или посылку»
   относится к шагу 1 пассажирского мастера «Новый заказ» (см. ниже) и на
   водительском шаге не используется.
2. Маршрут: «Точка посадки», промежуточные точки посадки, «Пункт назначения»,
   «Добавить остановку», дата и время выезда, примерное время прибытия,
   количество мест (начинается с 0). Крестик в поле очищает точку посадки и
   пункт назначения, а промежуточную остановку удаляет целиком.
3. Стоимость: цена всего маршрута, цены между остановками и стоимость посадки.
4. Автомобиль: список авто, прошедших проверку, и расчёт по деньгам сверху.
5. Дополнительные услуги: детское кресло, багаж, животные и посылка.
6. Тип бронирования: стандартное или быстрое, публикация поездки.

Цены дополнительных услуг задаёт платформа, а не водитель: он только включает
услугу тумблером и видит её стоимость (в превью — 150 ₽ за кресло, багаж и
животных). Посылка настраивается в отдельном листе: размеры «Маленькая» 150 ₽,
«Средняя» 250 ₽, «Большая» 350 ₽ и переключатель «Без проезда пассажира». Пока
размер не выбран, в строке услуги показывается «до 350 ₽».

Публикация происходит на шаге 6 кнопкой «Опубликовать поездку». Вторая кнопка —
«Сохранить шаблон»: в тестовой реализации шаблон сохраняется тем же черновиком в
«Мои поездки», откуда поездку можно открыть, дозаполнить и опубликовать.

Обязательна только цена всего маршрута: цены между остановками и стоимость
посадки водитель заполняет по желанию, незаполненный участок отдельно не
продаётся.

Введённая водителем цена — это сумма, которую получает **водитель**. Комиссия
платформы начисляется **сверху**, и пассажир платит их сумму: 1000 + 10 % = 1100.
Формула раздела 16.3 ТЗ при этом сохраняется, потому что `total_price` — это
сумма к оплате пассажиром: `driver_amount = total_price - commission_amount`
(1100 − 100 = 1000).

Комиссия задаётся процентом в `app_settings.commission_percent` (сейчас 10) и
считается на сервере при создании бронирования; клиент только показывает
расчёт. Плитки на шагах 3 и 4 читаются как «Общая стоимость» 1100,
«Комиссия 10 %» +100, «Вы получите» 1000.

Комиссия начисляется на итог по участку вместе с доп. услугами и на посылку.
При выключенной монетизации (`monetization_enabled = false`) комиссия равна
нулю и пассажир платит ровно цену водителя.

Макет шага 4 пока не предоставлен: его содержание разложено по правилам выше, а
вёрстка использует токены шагов 1-3 и подлежит правке по Figma.

Технические решения тестовой реализации, вытекающие из этих правил (ТЗ их
подробно не специфицирует):

- Цены хранятся в `trips.fare_table` — объект вида `{"0-2": 850}`, где ключ это
  позиции двух точек маршрута. Стоимость проезда с точки `i` до точки `j` — это
  ровно значение `"i-j"`, поднятое до минимальной стоимости «за посадку», если
  она выше. Ничего не суммируется. Цена всего маршрута — та же таблица, ключ
  `"0-<последняя точка>"`, и она обязательна для публикации.
- При добавлении остановки уже заданные цены сохраняются и переадресуются на
  сдвинувшиеся точки, а новые пары остаются пустыми. При удалении остановки
  исчезают только цены, которые её касались.
- Примерное время прибытия задаётся временем суток и берёт день у выезда; если
  указанное время уже прошло в день выезда, прибытие переносится на следующий
  день.
- Сохранение и публикация работают над одной записью поездки: публикация меняет
  статус черновика, а не создаёт вторую поездку. Обратная поездка создаётся
  отдельной записью со ссылкой на исходную (`paired_trip_id`).
- Неделя в лимите публикаций считается скользящим окном в 7 дней, пока сервер не
  задал собственное правило.
- Оплата остаётся mock-действием на сервере: онлайн-эквайринг в тестовом scope
  не подключается, платёжный SDK не добавляется.

## Создание заказа пассажиром

У пассажира есть собственный мастер «Новый заказ» из 4 шагов, он открывается
зелёной кнопкой «+» в нижней навигации и не имеет отношения к водительскому
мастеру из 6 шагов.

1. Тип заказа: «Автомобиль — найти водителя для себя» или «Автобус — отправить
   груз или посылку».
2. Маршрут: точка посадки, промежуточные точки, пункт назначения, «Добавить
   остановку», дата и время выезда, примерное время прибытия и количество мест.
3. Дополнительные услуги: для заказа места — животные, багаж и детское кресло
   по ценам платформы; для посылки — размер S / M / L. Пока размер не выбран,
   «Далее» неактивна.
4. Проверка заказа: маршрут, дата и время, количество мест или размер посылки,
   выбранные услуги и кнопка «Найти поездки». Она применяет маршрут и тип
   транспорта как фильтры поиска и открывает «Поездки».

Пассажирский заказ — это поиск уже опубликованной поездки, а не вторая сущность
поездки: бронирование места и отправка посылки происходят в карточке поездки,
поэтому мастер не создаёт на сервере ничего, чего бэкенд не видит.

Новый заказ начинается с пустого маршрута: адреса из макета — это mock-контент,
подставлять их в черновик нельзя, иначе «Далее» активна с чужими адресами.

## Отправка посылки

На карточке поездки, водитель которой возит посылки, кнопка «Отправить посылку»
открывает свой лист: точки передачи и получения, размер S / M / L и
комментарий водителю. Посылка не занимает пассажирское место
(`seat_count = 0`), а её стоимость берётся из каталога платформы
(`app_settings.parcel_size_specs`), а не из цены поездки и не от водителя.
Дальше заявка идёт тем же путём, что и место: подтверждение водителя при
стандартном бронировании и mock-оплата.

## Разделы профиля

Все пункты «Профиля» рабочие, заглушек нет.

- **Сохранённые маршруты** — пары «откуда → куда», хранятся на устройстве и
  открывают поиск поездок по этому маршруту.
- **История заказов** — завершённые заказы пассажира и завершённые поездки
  водителя; отдельной сущности не заводится, берутся те же записи.
- **Жалобы** — обращения пользователя с темой и текстом, коллекция
  `complaints`. Создание и чтение идут через серверные маршруты, статус и автора
  клиент задать не может; ответ администратора виден в карточке.
- **Уведомления** — записи `notifications` пользователя. Отметка о прочтении —
  серверное действие `POST /api/app/notifications/read`, `updateRule` коллекции
  остаётся закрытым. Счётчик непрочитанных выводится бейджем в профиле.
- **Способ оплаты** — карты для mock-оплаты, хранятся на устройстве. Полный
  номер карты не сохраняется: только последние четыре цифры и срок действия,
  потому что платёжный провайдер не подключается.
- **Частые вопросы** — статичный список, ответы описывают правила, которые
  приложение реально применяет.
- **О приложении** — версия, сборка и переходы к условиям использования и
  политике конфиденциальности.

## Дубли поездок и активная регистрация

Если у нас две одинаковые поездки (совпадают маршрут, дата и время отправления),
пассажиру показываются **обе**. Активной для загрузки (набора пассажиров) в один
момент является только одна из них: у неё зелёная подпись «идёт регистрация».
Вторая поездка видна в списке, но забронировать её нельзя, пока активна первая.

Признак активной поездки определяет backend, клиент только отображает его: два
дубля не должны одновременно принимать бронирования.

## Отображение сумм пассажиру при включённой монетизации

Монетизация включается серверной настройкой (`app_settings`, feature flag).
Когда она включена, пассажир видит суммы поэтапно:

1. В карточке и деталях поездки водителя — общую стоимость поездки.
2. Когда приходит запрос на оплату бронирования — сумму комиссии, которую нужно
   оплатить (онлайн-эквайринг, в тестовом scope mock).
3. После оплаты комиссии — три суммы: общую стоимость, комиссию и сумму к
   оплате водителю.

Суммы считает backend: `driver_amount = total_price - commission_amount`
(раздел 16.3 ТЗ). При выключенной монетизации пассажиру показывается только
общая стоимость поездки.

Уточнение к разделу 13 ТЗ: онлайн оплачивается именно комиссия за бронирование,
а не вся стоимость поездки; сумма к оплате водителю остаётся расчётом вне
онлайн-платежа.

В списке автомобилей на шаге 4 показываются только авто со статусом `approved`.
Если проверенных авто нет, вместо списка выводится состояние «Нет добавленных
авто» с кнопкой «Добавить авто» и пояснением про СТС.

## Водитель. Мои автомобили

Раздел «Транспортные средства» открывается из профиля водителя и содержит:

- пустое состояние «У вас еще нет транспортного средства» с кнопкой
  «Добавить ТС»;
- список авто аккаунта: фото, марка и модель, отметка проверки, госномер и
  количество мест;
- карточку авто: фото, название, госномер, статус проверки, тип и количество
  мест, блок «Документы» со строкой СТС и кнопкой «Заменить», а также действия
  «Редактировать» и «Удалить ТС».

Правила тестовой реализации:

- Новое авто попадает в гараж со статусом «На проверке», если СТС загружено, и
  «Черновик», если нет. Проверку выполняет администратор — приложение статус не
  назначает само.
- Любое редактирование авто и замена СТС возвращают его на проверку.
- Для публикации поездки доступны только авто со статусом «Проверен», поэтому
  правка авто снимает его из выбора в мастере до новой проверки.
- Удаление ТС подтверждается диалогом: действие необратимо, а опубликованные
  поездки на этом авто остаются без изменений.
- Экран «Добавление нового ТС» состоит из блоков «Информация об автомобиле»
  (марка, модель, вместимость, фото), «Тип» (легковой или автобус) и
  «Подтверждающие документы». Кнопка «Добавить» активна, когда выбраны марка,
  модель, вместимость и тип.
- Марка и модель выбираются из справочника в отдельном листе с поиском: список
  марок сгруппирован по буквам, поиск отбирает совпадения по началу названия
  («i» → Infiniti, Isuzu, Iveco). Модели показываются для выбранной марки, смена
  марки сбрасывает модель.
- Фото загружается через лист «Загрузка фотографии» (камера или файлы) и
  снимается крестиком на превью.
- Госномера в макете формы нет: он не вводится вручную и заполняется по данным
  СТС при проверке. Пока номера нет, в списке и карточке показывается только
  вместимость.

## Водитель. Управление бронированием

При стандартном бронировании заявка пассажира приходит водителю как отклик:

- на экране «Мои поездки» показывается уведомление «Новый отклик» с текстом
  «Пассажир хочет присоединиться к вашей поездке. Ожидается ваше решение.» и
  кнопкой «Перейти к отклику»; уведомление показывается один раз на заявку;
- экран отклика повторяет поездку: стоимость, комиссия и сумма к оплате
  водителю, «Маршрут поездки» с раскрывающимися остановками, «Маршрут
  пассажира» с точками посадки и высадки, дата, время, свободные места и
  примерное время прибытия;
- решение принимается кнопками «Отклонить бронь» и «Подтвердить бронь»; из
  шапки можно перейти в профиль пассажира до решения.

Правила тестовой реализации:

- Заявка, ожидающая решения, не занимает место: места считаются только по
  подтверждённым броням, поэтому до подтверждения свободных мест не убывает.
- Подтверждение переводит бронь в подтверждённые и занимает места; отклонение
  удаляет заявку из поездки.
- Заявки принимаются только опубликованными поездками — черновик их не
  получает.
- Если у пассажира не указаны свои точки посадки и высадки, считается, что он
  едет весь маршрут — от первой точки до последней.
- После решения водитель попадает на экран поездки, где показывается зелёное
  уведомление «Бронь подтверждена» или «Бронь отклонена».
- В списке пассажиров у каждой брони видно, чьего действия ждут: «Подтвердите
  бронь» красным — ждут решения водителя, «Ожидает оплаты» зелёным — бронь
  подтверждена и ждёт оплаты пассажиром, «Оплачено» — ничего не требуется.

## Профиль пассажира и чат

Профиль пассажира открывается водителем из заявки и из списка пассажиров и
имеет два состояния:

- до решения по заявке видны только имя, фото и «Рейтинг поездок»;
- после подтверждения брони добавляются «Номер телефона» и блок «Маршрут
  пассажира» с точками посадки и высадки.

Так выполняется требование ТЗ не раскрывать телефон другого пользователя без
основания: контакт открывается только тогда, когда пассажир едет с водителем.

Кнопка «Написать» открывает чат с этим пассажиром: чат создаётся при первом
обращении и переиспользуется дальше, отдельная переписка ведётся на каждую
поездку. В разделе «Чаты» показываются только переписки с сообщениями, свежие
сверху; пустой чат и пустой список объясняют, что делать.

Когда пассажир оплачивает подтверждённую бронь, водитель видит уведомление
«Пассажир оплатил поездку» с переходом к поездке; в списке пассажиров бронь
получает статус «Оплачено». Уведомление показывается один раз.

В тестовой реализации чаты и сообщения живут в памяти: realtime-подписка и
коллекции PocketBase появятся вместе с backend.
