# 1. Цель проекта

Реализовать работоспособный мобильный MVP приложения **«Путь»** по предоставленному Figma-прототипу.

Приложение объединяет сценарии пассажира и водителя:

- поиск поездок;
- просмотр деталей поездки;
- бронирование места;
- создание и управление поездками водителем;
- добавление автомобиля;
- подтверждение/отклонение бронирований;
- mock-оплата без подключения платежного провайдера;
- отмена бронирования;
- чат между участниками;
- работа с профилем;
- базовые сценарии перевозки посылок и дополнительных услуг;
- хранение полноценной модели отзывов в backend, несмотря на отсутствие UI для их создания в тестовой версии.

Основной критерий готовности — приложение должно воспроизводить ключевые пользовательские сценарии из Figma и работать на реальном устройстве, подключаясь к удаленно развернутому PocketBase.

# 2. Обязательные ограничения тестового задания

Эти требования имеют приоритет над любыми предположениями, которые могут возникнуть из макетов.

## 2.1. Отзывы и рейтинг

В тестовой версии **не реализуется интерфейс создания/редактирования отзывов**.

При этом backend и структура БД должны поддерживать полноценные отзывы для последующего развития продукта.

Правило отображения рейтинга:

- если у пользователя есть опубликованные отзывы — показывать фактический средний рейтинг и количество отзывов;
- если отзывов нет — отображать строго по бизнес-правилу:

> **5 звезд, нет отзывов**

При `reviews_count = 0` нельзя выводить `0`, `—`, `Нет рейтинга`, `0.0` и т. п.

Рекомендуется не записывать в БД фиктивный рейтинг `5.0`. На уровне данных отсутствие отзывов должно оставаться отсутствием отзывов, а значение `5 звезд` является только правилом отображения.

---

## 2.2. SMS и код подтверждения

Внешний SMS-провайдер **не подключается**.

Для любого номера телефона в тестовой версии код подтверждения всегда:

```text
111111
```

Требования:

- кнопка «Получить код» должна визуально работать;
- после запроса кода пользователь переходит на экран ввода SMS-кода;
- код `111111` считается корректным для любого допустимого номера телефона;
- любой другой код показывает состояние ошибки, предусмотренное макетом;
- повторная отправка кода может имитироваться локальным таймером;
- фактическое SMS не отправляется;
- код не должен зависеть от страны, оператора или номера телефона.

---

## 2.3. Оплата

Платежный провайдер, эквайринг, Apple Pay, Google Pay, банковские SDK и формы ввода карты **не подключаются**.

При нажатии пользователем кнопки **«Оплатить»**:

1. frontend вызывает backend-action mock-оплаты;
2. backend проверяет, что бронирование находится в статусе, допускающем оплату;
3. создается/обновляется запись `payment`;
4. `payment.status` становится `paid`;
5. `booking.payment_status` становится `paid`;
6. бронирование переходит в подтвержденный статус;
7. пользователь сразу видит состояние **«Оплачено»**.

Никаких редиректов на платежные страницы быть не должно.

Mock-операция должна оставаться серверной, чтобы бизнес-логика перехода статусов не находилась только во Flutter-клиенте.

---

## 2.4. Хостинг

Проверка приложения будет выполняться **на устройстве вне РФ**.

Поэтому:

- размещение backend на российском хостинге не требуется;
- допускается любой VPS/PaaS, доступный из интернета;
- PocketBase должен быть доступен по публичному HTTPS URL;
- нельзя рассчитывать на `localhost`, локальную Wi-Fi сеть разработчика или VPN;
- сертификат HTTPS должен быть валидным;
- приложение должно работать с backend без привязки к российским сервисам.

# 3. Источник истины и приоритет требований

При реализации использовать следующий порядок приоритетов:

1. требования этого ТЗ;
2. явные условия тестового задания;
3. состояния и пользовательские потоки Figma;
4. технические решения, описанные в этом ТЗ;
5. если поведение не определено ни в ТЗ, ни в макете — использовать максимально простое и предсказуемое поведение без добавления лишнего функционала.

Если тексты/термины в Figma противоречат технической модели, UI может сохранять формулировку макета, но backend должен использовать однозначные сущности.

Например, слово **«заказ»** в макете встречается в разных смыслах. В backend необходимо разделять:

- `Trip` — поездка, опубликованная водителем;
- `Booking` — бронирование/заявка пассажира;
- `Payment` — оплата бронирования;
- `Parcel` — данные посылки, если бронирование относится к перевозке посылки.

# 5. Технологический стек

## 5.1. Mobile

Обязательно:

- **Flutter**;
- Dart версии, совместимой с актуальной стабильной Flutter SDK;
- одна кодовая база для iOS и Android.

Рекомендуемые библиотеки:

- `pocketbase` — официальный/поддерживаемый Dart-клиент PocketBase;
- `flutter_riverpod` — управление состоянием;
- `go_router` — навигация;
- `freezed` + `json_serializable` — модели, если используются codegen-модели;
- `image_picker` — фото профиля/автомобиля/СТС;
- `geolocator` — доступ к координатам устройства;
- `permission_handler` — разрешения, если требуется;
- `intl` — даты/форматирование.

Допускается эквивалентная реализация, если не усложняет проект.

## 5.2. Backend

- **PocketBase** актуальной стабильной версии на момент разработки;
- встроенная SQLite БД PocketBase;
- PocketBase Collections;
- PocketBase File Storage;
- PocketBase Realtime для чатов/обновлений, где это удобно;
- PocketBase migrations;
- PocketBase hooks/custom routes для бизнес-операций, которые нельзя безопасно выполнять простым CRUD из мобильного клиента.

## 5.3. Не использовать

В рамках тестового задания не требуется подключать:

- Firebase Auth;
- Firebase Cloud Messaging;
- внешний SMS gateway;
- Stripe/ЮKassa/CloudPayments и другие платежные сервисы;
- отдельный PostgreSQL;
- отдельный backend на NestJS/Node.js;
- российский хостинг как обязательное условие.

PocketBase является единым backend для MVP.

# 8. Авторизация и онбординг

## 8.1. Первый запуск

По Figma присутствуют:

- стартовый экран приложения «Путь»;
- onboarding-слайды;
- CTA «Начать» / «Продолжить»;
- вариант «Уже есть аккаунт»;
- выбор роли «Водитель» / «Пассажир»;
- выбор города;
- регистрация/вход по телефону;
- создание профиля;
- загрузка фотографии.

## 8.2. Номер телефона

Приложение адаптировано под РФ: ввод номера телефона рассчитан только на
формат `+7` (10 значащих цифр после кода страны).

Требования:

- сохранять номер в нормализованном формате (`+7XXXXXXXXXX`);
- поле `phone` должно быть уникальным;
- UI принимает только номера в формате `+7`; ведущие `7` или `8`,
  введённые вручную, распознаются как код страны/внутренний префикс и
  отбрасываются;
- форматирование UI зависит от введённого номера, но backend должен хранить
  нормализованное значение.

## 8.3. Получение кода

Custom backend action:

```http
POST /api/app/auth/request-code
```

Пример payload:

```json
{
  "phone": "+79123456789"
}
```

Ответ:

```json
{
  "success": true,
  "expiresIn": 60
}
```

SMS не отправлять.

## 8.4. Проверка кода

```http
POST /api/app/auth/verify-code
```

Payload:

```json
{
  "phone": "+79123456789",
  "code": "111111"
}
```

Правила:

- если `code == 111111` — код верный;
- иначе вернуть бизнес-ошибку `INVALID_OTP`;
- если пользователь существует — авторизовать;
- если пользователя нет — создать аккаунт и вернуть авторизованную сессию;
- клиент получает стандартный auth token PocketBase или эквивалентную серверную сессию PocketBase.

Внутренняя реализация auth может использовать служебные поля/пароль PocketBase, но общий пароль не должен быть видим пользователю и не должен выступать пользовательским способом входа.

## 8.5. Таймер повторной отправки

- UI показывает countdown, например 59 секунд;
- по окончании разрешается повторить request-code;
- backend не обязан отправлять реальное сообщение;
- повторный запрос не меняет код — он остается `111111`.

## 8.6. Создание профиля

Поля:

- имя — обязательно;
- аватар — опционально;
- город — обязательно;
- выбранная роль — обязательно на первом входе.

Если фото не загружено — использовать нейтральный placeholder.

# 10. Поиск поездок пассажиром

## 10.1. Список поездок

По Figma поддерживаются состояния:

- поездки есть;
- поездок нет;
- фильтр применен, результатов нет;
- доступ к локации запрошен/отклонен/разрешен.

Карточка поездки должна поддерживать отображение:

- имя водителя;
- рейтинг;
- количество отзывов/состояние отсутствия отзывов;
- расстояние до места отправления;
- бейджи вроде «Топ» / «Ближайший», если такие данные рассчитаны;
- точка отправления;
- промежуточные остановки;
- точка назначения;
- дата и время отправления;
- примерное время прибытия;
- цена на человека;
- доступные дополнительные услуги;
- доступность мест.

## 10.2. Правило рейтинга в карточке

```text
reviews_count == 0
→ "5 звезд, нет отзывов"
```

Если отзывы есть:

```text
rating_avg = 4.5, reviews_count = 12
→ "4.5, 12 отзывов"
```

Точные склонения `отзыв / отзыва / отзывов` реализовать корректно.

## 10.3. Автомобили и автобусы

В Figma присутствуют вкладки:

- `Автомобили`;
- `Автобусы`.

Модель данных должна поддерживать `transport_type`.

Обязательный полностью рабочий сценарий тестового задания — легковой автомобиль, поскольку именно для него подробно задан сценарий создания поездки.

Для автобусов допускается:

- отображать данные, если они заведены в PocketBase;
- корректно отображать empty state, если данных нет.

Не требуется придумывать отдельный сложный flow создания автобусного рейса, если его нет в макете.

## 10.4. Фильтры

Backend-модель должна позволять фильтровать минимум по:

- типу транспорта;
- городу;
- точке отправления;
- точке назначения;
- дате;
- количеству требуемых мест;
- дополнительным услугам;
- типу бронирования;
- диапазону цены, если соответствующий контрол есть в макете.

Фильтры должны применяться на уровне запроса к backend, а не только скрывать уже загруженные карточки локально.

## 10.5. Сортировка

Допускаются:

- ближайшие;
- по времени отправления;
- по цене;
- «топ» на основе простого scoring.

Если Figma не требует выбора сортировки пользователем, достаточно реализовать стабильный default order.

# 12. Бронирование

## 12.1. Типы бронирования

В Figma заданы два режима.

### Стандартное бронирование

Flow:

```text
Пассажир создает заявку
→ Водитель получает заявку
→ Водитель смотрит пассажира
→ Водитель подтверждает или отклоняет
→ При подтверждении пассажиру доступна оплата
→ Пассажир нажимает «Оплатить»
→ Mock payment
→ Бронь подтверждена
```

### Быстрое бронирование

Flow:

```text
Пассажир выбирает поездку
→ Создается бронирование
→ Подтверждение водителя не требуется
→ Пассажир нажимает «Оплатить»
→ Mock payment
→ Бронь подтверждена
```

## 12.2. Статусы бронирования

Использовать enum/select:

```text
draft
pending_driver
rejected_by_driver
awaiting_payment
confirmed
cancelled_by_passenger
cancelled_by_driver
completed
expired
```

Отдельно хранить:

```text
payment_status:
not_required | unpaid | paid | refund_requested | refunded
```

Не смешивать статус бронирования со статусом оплаты.

## 12.3. Проверка мест

При создании или подтверждении бронирования backend обязан проверить, что мест достаточно.

Нельзя доверять только значению, отображенному клиентом.

Для предотвращения двойной продажи последнего места критическая операция должна выполняться серверно и атомарно/транзакционно средствами PocketBase/SQLite.

Количество занятых мест рассчитывается только по бронированиям, которые действительно резервируют место согласно текущему статусу.

## 12.4. Повторный запрос

Создание одного и того же бронирования двойным тапом не должно приводить к двум активным броням.

Backend-action должен быть идемпотентным либо выполнять проверку существующего активного бронирования данного пользователя на ту же поездку.

# 13. Mock-оплата

## 13.1. Backend action

```http
POST /api/app/bookings/{bookingId}/pay
```

Условие:

- пользователь является пассажиром данного бронирования;
- бронь в `awaiting_payment`;
- оплата еще не завершена.

Результат:

```text
payment.status = paid
payment.provider = mock
payment.paid_at = now
booking.payment_status = paid
booking.status = confirmed
```

Рекомендуется генерировать `mock_transaction_id`, например UUID.

## 13.2. Повторное нажатие

Endpoint должен быть идемпотентным.

Если платеж уже `paid`, повторный вызов возвращает текущее успешное состояние, а не создает второй платеж.

## 13.3. UI

После успешного ответа:

- CTA «Оплатить» исчезает;
- отображается состояние **«Оплачено»**;
- бронь попадает в активные/подтвержденные.

# 14. Отмена бронирования и ограничения

В Figma присутствует сценарий отмены брони и отдельное состояние после двух отмен за последние 30 дней.

## 14.1. Отмена

При отмене:

- `booking.status = cancelled_by_passenger`;
- сохраняется `cancelled_at`;
- сохраняется причина, если предусмотрена UI;
- место становится доступным для других пассажиров.

Если бронь была оплачена:

- `booking.payment_status = refund_requested`;
- создается `refund`;
- реальный возврат денег не выполняется;
- UI показывает экран по Figma о том, что заявка на возврат отправлена администратору.

## 14.2. Возврат

Коллекция `refunds` должна поддерживать статусы:

```text
requested
approved
refunded
rejected
```

В тестовом задании физического перевода денег нет.

Администратор при необходимости меняет статус через PocketBase Admin UI.

## 14.3. Две отмены за 30 дней

Правило из макета:

- если пользователь отменил две поездки за последние 30 дней, новое бронирование временно недоступно.

Так как точная длительность блокировки в доступном макете не определена, для тестового задания принять простое правило:

> после достижения лимита ставится `booking_blocked = true`; снять ограничение может администратор через PocketBase.

UI показывает экран/сообщение из Figma о временной блокировке и передаче информации администратору.

Подсчет отмен должен производиться на backend.

# 16. Создание поездки водителем

Основной wizard следует Figma.

## 16.1. Общие требования

Создание должно быть пошаговым.

Черновик желательно сохранять локально во Flutter до публикации либо в `trips.status = draft`, чтобы возврат назад между шагами не терял данные.

## 16.2. Маршрут

Водитель задает:

- точку посадки;
- пункт назначения;
- 0..N промежуточных остановок;
- дату отправления;
- время отправления;
- примерное время прибытия;
- количество мест.

Каждая точка маршрута должна иметь:

- отображаемый адрес;
- город;
- latitude;
- longitude;
- порядок.

Если внешняя геокодинг-служба не используется, разрешается выбирать точки из тестового справочника/сохранять адрес с координатами вручную.

## 16.3. Цена

Хранить:

- базовую цену для пассажира;
- комиссию платформы;
- сумму водителю.

Формула:

```text
driver_amount = total_price - commission_amount
```

Даже при mock-оплате финансовые поля должны быть отдельными.

## 16.4. Дополнительные услуги

По Figma модель должна поддерживать:

- детское кресло;
- багаж;
- животные;
- посылка;
- дополнительную стоимость услуги.

Список услуг не следует зашивать в отдельные boolean-поля поездки. Лучше использовать справочник `extra_services` и связующую коллекцию `trip_extra_services`.

## 16.5. Режим бронирования

```text
standard
instant
```

UI-тексты соответствуют макету:

- Стандартное;
- Быстрое бронирование.

## 16.6. Автомобиль

Для публикации поездки на легковом автомобиле водитель должен выбрать автомобиль со статусом `approved`.

Если автомобиля нет, показывается состояние из Figma с CTA «Добавить авто».

Если автомобиль есть, показываются данные автомобиля и количество мест.

## 16.7. Публикация

Перед публикацией backend проверяет:

- водитель авторизован;
- профиль заполнен;
- выбран допустимый автомобиль;
- автомобиль прошел проверку;
- маршрут валиден;
- дата поездки не в прошлом;
- мест > 0;
- цена валидна;
- лимиты публикации не превышены.

После публикации:

```text
trip.status = published
published_at = now
```

Показывается экран успеха `Заказ опубликован!`/соответствующая формулировка Figma.

# 17. Лимиты публикаций

В Figma присутствуют счетчики лимитов, в том числе дневные/недельные и счетчики прямого/обратного маршрута.

Не хардкодить значения по всему Flutter-коду.

Создать серверную конфигурацию, например `app_settings`:

```json
{
  "driver_trip_limit_per_day": 2,
  "driver_trip_limit_per_week": 10,
  "outbound_limit_per_pair": 1,
  "return_limit_per_pair": 1
}
```

Значения являются тестовыми default-настройками и могут быть изменены администратором без релиза приложения.

Backend является источником истины по счетчикам.

# 18. Обратный маршрут

После публикации водитель может нажать «Добавить обратный маршрут».

Новая поездка:

- создается как отдельный `trip`;
- имеет ссылку `paired_trip_id` на исходную поездку;
- маршрут копируется в обратном порядке;
- водитель задает новую дату/время;
- остальные параметры могут быть предзаполнены из исходной поездки;
- перед публикацией проходят обычные проверки.

---

# 19. Редактирование поездки

В Figma предусмотрен flow редактирования.

Для тестовой реализации:

- `draft` — можно редактировать все поля;
- `published` без подтвержденных/оплаченных броней — можно редактировать основные поля;
- если уже есть `confirmed` бронирования — изменение критичных параметров (маршрут, дата, время, цена, автомобиль) запрещается;
- некритичные поля можно менять, если это не нарушает бронирование.

При попытке запрещенного изменения показать понятную ошибку.

Такое ограничение является техническим правилом тестовой реализации, поскольку изменение параметров уже оплаченной поездки в макете подробно не специфицировано.

# 20. Автомобили водителя

## 20.1. Данные автомобиля

Минимальные поля:

- марка;
- модель;
- госномер;
- цвет — опционально;
- год — опционально;
- количество пассажирских мест;
- фото автомобиля — опционально;
- файл/фото СТС — обязательно для отправки на проверку;
- статус проверки.

## 20.2. Статусы

```text
draft
pending
approved
rejected
```

## 20.3. Верификация

Flow:

```text
Водитель добавляет автомобиль
→ загружает СТС
→ отправляет на проверку
→ status = pending
→ администратор проверяет через PocketBase
→ approved / rejected
```

Только `approved` автомобиль допускается к публикации поездки.

Для `rejected` хранить `verification_comment`.

Перевозка запрещенных категорий, юридические проверки содержимого и интеграция с логистическими сервисами в тестовое задание не входят.

# 22. Чаты

В нижнем меню Figma присутствует раздел «Чаты».

Для MVP реализовать текстовый чат между пассажиром и водителем.

## 22.1. Чат создается

Чат может создаваться:

- либо при первом сообщении по конкретному бронированию.

## 22.2. Сообщения

Минимально поддержать:

- текст;
- автора;
- timestamp;

## 22.3. Realtime

Для новых сообщений использовать PocketBase Realtime subscription.

Push-уведомления APNs/FCM для тестового задания не обязательны.

Если приложение открыто — новое сообщение должно появляться без ручного refresh.

# 25. Отзывы: полноценная backend-модель

Несмотря на отсутствие UI добавления отзывов, создать коллекцию `reviews` так, чтобы в будущем можно было включить функционал без миграции основной модели.

## 25.1. Поля review

| Поле | Тип | Обязательно | Описание |
|---|---|---:|---|
| `author_id` | relation → users | да | Автор отзыва |
| `target_user_id` | relation → users | да | Пользователь, которому оставлен отзыв |
| `trip_id` | relation → trips | да | Поездка |
| `booking_id` | relation → bookings | да | Подтверждение факта совместной поездки |
| `rating` | number | да | 1–5 |
| `text` | text | нет | Текст отзыва |
| `status` | select | да | `pending/published/rejected` |
| `created_at` | auto date | да | Дата создания |
| `updated_at` | auto date | да | Дата изменения |

## 25.2. Ограничения

- `rating` только 1..5;
- автор не может оставить отзыв самому себе;
- отзыв возможен только по существующему бронированию;
- в будущей реализации отзыв допускается только после завершенной поездки;
- одна сторона может оставить не более одного отзыва другой стороне по одному booking;
- средний рейтинг рассчитывается только по `published` отзывам.

## 25.3. UI тестовой версии

В мобильном приложении **не создавать**:

- кнопку «Оставить отзыв»;
- форму оценки;
- редактирование отзыва;
- удаление отзыва.

Допускается только чтение уже существующих тестовых отзывов.

- `chats.booking_id` unique;
- `messages.chat_id + created_at`;
- `reviews.target_user_id + status`;
- unique review constraint.

Удаление связанных данных должно быть осторожным.

Предпочтительно использовать soft-status (`cancelled`, `is_active=false`) для бизнес-сущностей, а не физическое удаление поездок/броней/платежей.

# 28. Правила доступа PocketBase

## 28.1. Пользователь

- может читать/изменять только собственные приватные данные;
- публично доступна только необходимая часть профиля;
- телефон другого пользователя не должен быть публичным полем.

## 28.2. Поездки

Публично авторизованным пользователям доступны только:

- `published` поездки;
- не прошедшие по времени;
- активного водителя.

Создавать/менять поездку может только ее водитель.

## 28.3. Автомобили

- изменение — только владелец;
- `verification_status` водитель сам менять на `approved` не может;
- изменение результата проверки — только admin/server hook.

## 28.4. Бронирования

Видеть бронирование могут:

- пассажир бронирования;
- водитель связанной поездки;
- администратор.

Критические переходы статусов выполнять server action, а не открытым update rule.

## 28.5. Платежи

Клиент не может напрямую записать `paid`.

Статус `paid` устанавливает только backend mock-payment action.

## 28.6. Чат

Чат и сообщения доступны только его двум участникам и администратору.

## 28.7. Отзывы

В тестовом клиенте create/update/delete отзывов закрыты.

Чтение `published` отзывов разрешено.

Администратор имеет полный доступ через PocketBase Admin UI.

# 34. Нефункциональные требования

## 34.1. Производительность

- список поездок — пагинация;
- не загружать всю базу поездок сразу;
- изображения с разумным размером/сжатием;
- loader при запросах;
- UI не должен блокироваться во время сетевых операций.

## 34.2. Сеть

- все запросы только HTTPS;
- backend URL задается через build config/env;
- не хардкодить localhost;
- предусмотреть request timeout;
- корректно отображать offline error.

## 34.3. Безопасность

Несмотря на тестовый характер:

- не хранить admin token PocketBase в приложении;
- не давать клиенту право менять server-controlled статусы;
- не публиковать СТС другим пользователям;
- не публиковать номер телефона в API списка поездок;
- использовать PocketBase access rules;
- хранить auth token штатным способом SDK/защищенного storage, если используется постоянная сессия.

Код `111111` является осознанным исключением только для тестовой версии.

## 34.4. Логи

Не логировать:

- auth token;
- файлы СТС;
- полные приватные данные пользователя.

Допускаются технические логи запросов/ошибок без чувствительных payload.

# 39. Acceptance Criteria

## AC-01. Первый вход

**Given** пользователь впервые установил приложение  
**When** проходит onboarding  
**Then** может выбрать роль, город и перейти к авторизации.

## AC-02. Код 111111

**Given** введен любой валидный номер  
**When** пользователь запрашивает код и вводит `111111`  
**Then** авторизация успешна без реального SMS.

## AC-03. Неверный код

**When** пользователь вводит любой код, кроме `111111`  
**Then** отображается ошибка неверного кода.

## AC-04. Новый пользователь

**Given** номера нет в базе  
**When** код `111111` подтвержден  
**Then** создается пользователь и открывается создание профиля.

## AC-05. Рейтинг без отзывов

**Given** у водителя 0 опубликованных отзывов  
**When** пассажир видит карточку/профиль  
**Then** отображается `5 звезд, нет отзывов`.

## AC-06. Рейтинг с отзывами

**Given** в БД есть опубликованные отзывы  
**Then** показывается фактический average rating и число отзывов.

## AC-07. Отзывы в БД

**Then** коллекция reviews существует и поддерживает автора, получателя, booking, trip, рейтинг, текст и moderation status, даже при отсутствии формы создания отзыва.

## AC-08. Поиск поездок

**Given** в базе есть будущие опубликованные поездки  
**When** пассажир открывает «Поездки»  
**Then** видит релевантные карточки.

## AC-09. Промежуточные остановки

**Given** поездка имеет 2 промежуточные остановки  
**Then** они отображаются в правильном порядке на деталях поездки.

## AC-10. Стандартная бронь

**When** пассажир отправляет заявку на standard trip  
**Then** водитель может approve/reject, а оплатить можно после approve.

## AC-11. Быстрая бронь

**When** пассажир бронирует instant trip  
**Then** подтверждение водителя не требуется.

## AC-12. Mock payment

**Given** бронирование ожидает оплаты  
**When** пользователь нажимает «Оплатить»  
**Then** без платежной формы статус становится `paid`, а UI показывает «Оплачено».

## AC-13. Idempotent payment

**When** «Оплатить» вызывается повторно  
**Then** второй платеж не создается.

## AC-14. Нет свободных мест

**Given** свободных мест недостаточно  
**When** пассажир пытается забронировать  
**Then** backend отклоняет операцию, даже если карточка в UI была устаревшей.

## AC-15. Создание поездки

**Given** водитель имеет approved автомобиль  
**When** проходит wizard и публикует поездку  
**Then** поездка становится доступна пассажирам.

## AC-16. Нет автомобиля

**Given** у водителя нет approved автомобиля  
**Then** публикация поездки невозможна, UI предлагает добавить автомобиль.

## AC-17. Верификация автомобиля

**When** водитель отправляет СТС  
**Then** status становится `pending`; администратор может изменить его на `approved/rejected`.

## AC-18. Обратная поездка

**When** водитель создает обратный маршрут  
**Then** создается отдельный trip с обратным порядком остановок и связью с исходной поездкой.

## AC-19. Отмена оплаченной брони

**When** пассажир отменяет paid booking  
**Then** создается mock refund request и показывается экран возврата по Figma; реальное движение денег отсутствует.

## AC-20. Две отмены

**Given** пользователь совершил две учитываемые отмены за 30 дней  
**Then** новые бронирования блокируются до административной разблокировки.

## AC-21. Чат

**Given** существует booking  
**When** пассажир или водитель отправляет сообщение  
**Then** второй участник видит его в чате, в открытом приложении — через realtime без ручного refresh.

## AC-22. Работа вне РФ

**Given** устройство находится вне РФ  
**When** приложение запущено через мобильный/обычный интернет  
**Then** авторизация, загрузка данных, создание и оплата mock-брони работают без VPN и локальной сети разработчика.

# 44. Примечание для разработчика

Главная цель тестовой реализации — не интегрировать максимальное количество внешних сервисов, а **корректно воспроизвести продуктовую логику и состояния Figma**.

Поэтому SMS, платежи и админские процессы намеренно упрощены, но структура данных и переходы состояний должны быть спроектированы так, чтобы позднее заменить mock-механизмы реальными интеграциями без переделки базовых сущностей.

Особенно важно не переносить неоднозначность UI-термина «заказ» в backend. Поездка, бронирование и платеж — разные сущности и разные жизненные циклы.
